# Sylla Voyage — Guidelines UX/UI

## 1. Objectif

L'interface de Sylla Voyage doit être simple, claire, humaine et accessible.

Elle doit permettre à une personne ayant une faible maîtrise du numérique de comprendre rapidement quoi faire.

---

## 2. Priorité mobile

L'expérience doit être pensée en priorité pour smartphone.

L'interface doit également rester utilisable sur :

- tablette ;
- ordinateur.

---

## 3. Simplicité

Chaque écran doit avoir un objectif principal clairement identifiable.

Éviter :

- les informations inutiles ;
- les interfaces trop chargées ;
- les menus complexes ;
- les tableaux de bord surchargés ;
- les fonctionnalités difficiles à comprendre.

---

## 4. Texte

Le texte doit être :

- court ;
- simple ;
- direct ;
- compréhensible.

Éviter les formulations techniques ou administratives lorsque des mots simples peuvent être utilisés.

---

## 5. Navigation

La navigation doit être évidente.

L'utilisateur doit pouvoir comprendre facilement :

- où il se trouve ;
- ce qu'il peut faire ;
- comment revenir en arrière ;
- quelle action est attendue.

---

## 6. Boutons et actions

Les actions principales doivent être clairement visibles.

Les boutons doivent :

- être suffisamment grands ;
- utiliser des libellés simples ;
- être facilement distinguables ;
- fournir un retour après l'action.

---

## 7. Icônes et éléments visuels

Les icônes peuvent être utilisées pour faciliter la compréhension.

Une icône ne doit pas être utilisée seule lorsqu'elle risque d'être ambiguë.

Les éléments visuels doivent avoir une fonction claire.

Aucun élément décoratif inutile ne doit être ajouté.

---

## 8. Accessibilité

L'interface doit prendre en compte les utilisateurs ayant une faible maîtrise de la lecture ou du numérique.

Privilégier :

- les grandes zones interactives ;
- les contrastes suffisants ;
- les informations visuelles ;
- les messages courts ;
- une hiérarchie visuelle claire ;
- des parcours simples.

---

## 9. États des interfaces

Les fonctionnalités importantes doivent prévoir au minimum les états pertinents :

- chargement ;
- succès ;
- erreur ;
- vide ;
- contenu disponible ;
- contenu verrouillé.

L'utilisateur doit toujours comprendre ce qui se passe.

---

## 10. Abonnement

Les contenus nécessitant un abonnement doivent être clairement identifiés.

Lorsqu'un utilisateur n'a pas accès à un contenu réservé :

- le contenu doit être identifiable comme verrouillé ;
- la raison du verrouillage doit être compréhensible ;
- l'action permettant de s'abonner ou de renouveler doit être clairement visible.

---

## 11. Professionnels vérifiés

Le statut de professionnel vérifié doit être clairement identifiable.

La présentation doit permettre au voyageur de distinguer facilement un professionnel vérifié d'un autre profil.

---

## 12. Publications

Les publications doivent être faciles à consulter.

La présentation doit privilégier :

- les informations essentielles ;
- les éléments visuels utiles ;
- une hiérarchie claire ;
- une action principale identifiable.

---

## 13. Messagerie

La messagerie doit être simple.

L'utilisateur doit pouvoir :

- voir ses conversations ;
- comprendre avec qui il échange ;
- envoyer un message ;
- envoyer un document ;
- consulter l'historique.

---

## 14. Documents

Les documents échangés doivent être facilement identifiables.

L'interface doit permettre de comprendre :

- quel document a été envoyé ;
- par qui ;
- quand ;
- comment le consulter lorsque l'utilisateur en a le droit.

---

## 15. Paiement

Le parcours de paiement doit être simple et transparent.

Avant la confirmation, l'utilisateur doit clairement voir :

- la formule choisie ;
- le prix ;
- les frais applicables ;
- le montant total.

Après le paiement, l'utilisateur doit recevoir un retour clair indiquant l'état de la transaction.

---

## 16. Formulaires

Les formulaires doivent être aussi courts que possible.

Ne demander que les informations nécessaires à l'action concernée.

Les champs obligatoires doivent être clairement identifiés.

Les erreurs doivent être expliquées avec des messages simples.

---

## 17. Messages d'erreur

Les erreurs doivent être compréhensibles par l'utilisateur.

Éviter les messages techniques tels que :

```text
Internal Server Error
Foreign Key Constraint
500
```
